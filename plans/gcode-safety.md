# G-code safety: verify what gets sent to printers

## Goal

Nothing FarmSlicer sends to a printer should be able to hurt the printer, the
plate, or the farm's schedule, whoever produced the file. Today three paths
put arbitrary G-code on a printer:

1. `POST /api/uploads`: any `.gcode.3mf`. `package::inspect` only reads the
   uploader's own metadata (`slice_info.config`), so print time, materials,
   printer model and nozzle, and therefore print rules, quotas and cost, are
   all self-declared.
2. Browser slicing: the client POSTs whatever G-code and package it likes to
   `/api/jobs/{id}/result`.
3. Server slicing: per-job overrides are merged without a key filter, so
   `machine_start_gcode`, `change_filament_gcode`, `filament_start_gcode`, ...
   inject G-code into slices FarmSlicer makes itself (custom profiles too).

The user asked for all of it ("do it all, boil the ocean"): lock down config
overrides, harden package parsing, verify every plate's G-code by simulating
it, use recomputed numbers instead of declared ones, and route findings
through the approval flow.

  under e2e runs without profiles: anything the checker needs must ship in the
  repo (generated data files), not be derived from profiles at runtime.

## Decisions already made (don't re-ask)

- Do all of it (user, 2026-10-12).
- **Allowlist, never a blocklist.** Bambu's own X1 start G-code uses `M500`,
  `M290`, `M201`/`M203`/`M205`, `M221`, `M900`, so "dangerous command" lists
  would block every real print. Allowed = what vendor templates and the slicer
  emit, with parameter ranges.
- **Data is generated, committed, and reviewable**: generated from the
  OrcaSlicer submodule's BBL profiles and BambuStudio's BBL profiles (pinned
  tag), by Rust code that shares the checker's tokenizer. A unit test fails
  when the Orca-derived file is stale (when profiles are present).
- **Severity**: `block` (can't be sent by anyone through FarmSlicer:
  malformed packages, zip tricks, commands that are never legitimate) vs
  `review` (needs an admin's approval) vs `info`.
- Safety findings need an **admin** to approve (it's the farm owner's
  hardware); group managers keep approving print-rule violations only.
- Admins sending directly must acknowledge findings (like
  `ignore_mapping_problems`).
- Every package is checked, server slices included (defense in depth; a
  finding on our own slice is an allowlist bug and is logged loudly).
- Print rules, quotas and cost use the larger of declared and recomputed
  print time, and recomputed filament use.

## Design

- **Overrides** (`src/config_policy.rs`): members may set only the
  settings-schema keys (`web/src/data/settings-schema.json`, also copied into
  the Docker server stage) within its ranges; admins may set any key except
  host-side ones (`post_process`, print-host keys). Same for custom profiles.
- **Package structure** (`src/package/zipcheck.rs`, `package::inspect`): the
  central directory must be unambiguous (unique names, also case-insensitively;
  no `..`/absolute/backslash names; stored or deflated; not encrypted) and its
  local entries must tile the file (no hidden entries a streaming unzipper
  would see). Plate MD5 is always computed; a `.md5` entry that disagrees =
  refused ("changed after slicing"). Plate G-code capped at 2 GiB.
- **Checker** (`src/gcode/`): `lex` reads lines like firmware (`G1X10`,
  `M620 S0A`; text commands like `M1002` are data); `check` simulates
  (positions incl. arcs, below-plate zones, temperatures vs declared
  materials and the model's own template temperatures, heated idle, dwells,
  filament per tool, planner time) and reports `block`/`review`/`info`;
  `data` holds the allowlist (`data/orca.json`, `data/bambustudio.json`
  generated by `harvest` from profiles; `data/slicer.json` hand-written).
- **Glue** (`src/safety.rs`): `check_job` runs on every recorded package and
  stores `Plate.check` in `package_json` (fingerprint = checker version +
  data hash + limits); `checked_package` re-checks stale plates before
  targets/send/approve; `spawn_recheck` at startup and on limits change;
  `settle_gcode_stats` for browser jobs without packages.
- **Sending**: blocked → 409 for everyone. Review → members' prints wait
  (`prints.safety_review`, only admins approve); admins must pass
  `acknowledge_review` (recorded as `approval_reason` + `decided_by`).
  `/targets` returns `blocked`, `needs_review`, `gcode_check`.
- **Numbers**: `PlateCheck.time_sec/grams/filament_g` = declared unless the
  G-code shows > 1.25x + 10 min / + 8 g; used by rules (`effective_time`),
  cost (`effective_grams`) and job stats (quotas).
- **Settings**: `gcode_limits` (max dwell 15 min, max heated idle 45 min,
  nozzle/bed margin 10 °C, reach margin 5 mm); `uploads` allow|review|deny
  (site + inherited group setting; admins and group managers exempt).

### Incident log (requested 2026-10-13) ✅

"Log if certain users upload custom G-code that fails or causes an error
during printing." A table `gcode_incidents` (user = whoever the G-code came
from, sender, job, print, printer, source, kind, severity, summary; a unique
`dedupe` key so re-checks and repeated printer reports don't duplicate),
written by `src/incidents.rs`, plus a server log line each:

- **Custom G-code** = uploaded files; server slices whose overrides set keys
  outside the Slice page's settings (an admin's start G-code); and any job
  whose check found something to hold it for (blocked/review), which is
  where tampered browser results show up. A clean browser slice is
  FarmSlicer's own engine's output, not custom.
- Kinds: `check` (blocked or review findings, logged for any source but a
  plain server slice); `print_failed` (the printer reported a failure, refused
  to start it, never started it; not "another print replaced it" or upload
  interruptions); `printer_error` (HMS / print error codes raised while it
  prints, once per code per print). Print kinds only for custom G-code.
- Admins: `GET /api/gcode-incidents?user=&limit=`; Users page shows each
  user's count and the list.

## Findings / gotchas

- Bambu Studio 02.05 X1 start G-code is dated 20251031; OrcaSlicer v2.4.2's is
  20250909. Newer Studio releases can use commands Orca's profiles don't, hence
  harvesting BambuStudio's profiles too.
- `slice_core` never runs `post_process` scripts (that's GUI code in
  `BackgroundSlicingProcess`), so no RCE today; still denied in overrides.
- Custom profiles aren't used for slicing yet (stored/edited only), and any
  full user can edit anyone's (see ISSUES.md).
- Real start G-code moves outside the printable area (Y -3..265 on X1, X up to
  255.6 for the cutter/chute) and to Z -1.5 (nozzle wipe); the movement
  envelope must come from the vendor templates.
- `M500` alone *is* vendor behaviour (`M500 ; save cali data` after levelling
  on A1/H2D/P1); only argument-shape and value rules can tell attacks apart.
- X1E start G-code flushes at a flat `M109 S290` for every material: the
  material temperature cap is raised to the model's hottest template literal
  (`template_nozzle_max`).
- Bambu Studio writes 20 kB comment lines (CONFIG_BLOCK); line limits apply to
  the command part only. Residual risk: firmware that splits overlong comment
  lines into chunks would run a chunk's tail; Bambu's own files rely on it not
  doing that.
- The `zip` crate silently lets a later duplicate entry win (IndexMap insert):
  hence our own central-directory reader.
- Time estimate vs Bambu Studio: 0.88-1.01x on real prints (16 h, 6 h, 40 min);
  0.5-0.9x on 5-20 min test prints (start calibrations aren't modelled). The
  under-estimate is the safe direction for "metadata understates" checks.
- Computed filament is a few grams above declared (purge lines count); the
  "understated" threshold has +8 g slack.
- Newer models (H2D, P2S, X2D) use computed positions in their templates, so
  their harvested `reach` is thin; FarmSlicer's own slices of them were clean
  anyway (single-filament). Multi-material H2D files are untested.
- Merged with the printer drivers (`plans/printer-drivers.md`, 2026-10-13):
  plain G-code packages go through `check_package` too, with
  `Declared::other_firmware`.
- **Every make gets a check; only Bambu gets Bambu's** (user, 2026-10-13).
  Other makes: `lex_other` (case-insensitive; Klipper `NAME KEY=VALUE`;
  Anycubic's `G9111 BEDTEMP=` macros; text args for M117/M862/M115/M98/
  M486); temperatures (M104/M109 S|R, SET_HEATER_TEMPERATURE, macro params
  with EXTRUDER/HOTEND/NOZZLE/BED/CHAMBER in the key); geometry from
  `data/printers.json` (371 printers, every non-BBL Orca vendor; short-name
  fallback "MK4S" → "Prusa MK4S"); firmware-generic hazards by value
  (measured against 59 vendors' templates: Prusa `M302 S160`, Artillery
  `M211 S1` and `SET_KINEMATIC_POSITION Y=0`, Lulzbot `M206 X0 Y0 Z0`,
  Dremel `M907` are vendor-normal; a printer's own template commands are
  exempt for it). Bambu-only: allowlist, unreadable-line block, line
  length, `blind_z` (deltas home at the top), 5 mm reach margin (others
  25 mm: deltas park at computed edges), Z floor -0.05 (others -0.5: Z
  offsets), material temperature caps by the printer's filament list
  (others: by material, lists are incomplete).
- Corpus for other makes (2026-10-13): 496 FarmSlicer slices across 53
  vendors, nothing held after the fixes above. Found on the way: Marlin's
  `M204 P`/`T` (Snapmaker sets `M204 S100` in start G-code, then P/T per
  feature: estimates were 1.8-2.5x), and profiles with machine limits of 0
  made `clamp(100, 0)` panic (never live: production had no per-printer
  data). Time median 0.99x, p90 1.20x, max 1.49x.
- Corpus tooling (not in the repo): `corpus.py` slices every Bambu machine
  profile × materials on a NO_AUTH container (port 9341 on buildhost, volume
  `farmslicer_gsafety_data`); `FARMSLICER_SAMPLE_PACKAGES=<dir> cargo test
  --release sample_packages_are_clean -- --nocapture` reports on a directory.

## Things not to do

- Don't hard-block commands just because they sound dangerous (`M500`).
- Don't trust anything inside an uploaded package to describe itself
  (`slice_info`, `project_settings`, `.md5`, CONFIG_BLOCK templates).
- Don't commit the maintainer's sample files or any real host names.
